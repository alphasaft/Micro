# Back to the forest
    
It's time to look at what `AST`s truly are. Usually, we don't really care : we just `$` them, without looking at their content. While that does work for most of the cases, but if we have to write complex macros, we might want to directly take a peak at `AST`s instead. Suppose, for example, we'd like to implement functions ; not only calls of preexisting functions, but also creation. How would we do that ? Obviously, we'd start with declaring a `fun'` macro : 

```js
// Declaration
{ name: "fun'", arity: [1, Infinity] }
```

To use like this (assuming the last statement automatically returns):

```
fun' add(x; y) { 
    x+y 
};

## Or, since brackets are optional
fun' add(x; y) x+y
```

But when you try to actually implement it, well, you can't do much. The only thing you might do with ASTs for now is to evaluate them, but obviously, that's not what you want here : you need to retrieve the parameter names to be able to bind them later. Luckily for us, AST manipulation makes it a piece of cake.

## AST dissection

We've already seen `AST`s representing macro calls, because they are passed down through macro reducers, but more generally speaking an `AST` is a plain JS object that always has two fields : `type` and `metadata`. `metadata` is another JS object indicating where and how that AST was parsed, but we won't cover it here. For now, let's focus on `type`. It can take three values, which serve to indicate what the `AST` represents : `"literal"`, `"operation"` and `"macro"`. Depending on that `type`, the `AST` will possess additionnal fields.

* A `literal` describes a literal generated by the compiler. It possesses a `value` field, filled with a string to represent that literal. So ``` `1` ``` would be `{ metadata: ..., type: "literal", value: "1" }`, for example.

* An `operation` describes... well, an operation. It has two additionnal fields : `operator` (`string`) and `operands` (`AST[]`). So `1+1` would be : `{ metadata: ..., type: "operation", operator: "+", operands: [{ AST for 1 }, { AST for 1 }] }` (notice how `{ AST for 1 }` would in fact again be an `"operation"` with operator `#number`).

* A `macro` describes a macro call. Its the only type of `AST` which you regularly take a look at, as it is these that are passed to `MacroReducer`s.

And there's nothing more to know ! When `$` is called on an `AST`, it checks the type, and performs the appropriate action : lifting a literal, applying the operator or calling the macro reducer.

> "Wait, if it's that simple, can I evaluate ASTs myself ?"

Yup ! You could even create `AST`s yourself, for that matter ! But one really interesting thing to do is to explore them.

## The big dive

Micro provides plenty of utility function to dig into `AST`s. I invite you to read the docs ; here we will just use `getLiteralOfName` to implement our function declarations. It takes an `AST` that corresponds to a ```[#name `name`]``` operation, and retrieves the `name` that was used, as a string.

```js

class DemoMicroRunner extends MicroTransformer {
    reducer = ({$}, { body }) => {
        // We introduce a `scope` field for our evaluator, representing the current scope.
        // Of course, in an actual language, we would want to implement it (far) better, but this will do.
        // We add this line to (re)initialize the scope every time we reduce a new script.
        this.scope = {}

        // ...
    }

    private funBindReducer = ({ $ }, { body, head: [functionNameAst, ...parametersAsts] }) => {
        // We extract the function name, which always is a literal...
        let functionName = functionNameAst.value
        
        // ...as well as the parameters names, which must be '#name' calls.
        let parameters = parametersAsts.map(getLiteralOfName)

        // Then we register the function in the scope
        this.scope[functionName] = (...functionArgs) => {
            if (functionArgs.length !== parameters.length) throw "Arguments count does not match parameters"

            // We copy the outer scope and add the parameters values
            let localScope = { ...this.scope }
            for (let i=0; i<functionArgs.length; i++) {
                localScope[parameters[i]] = functionArgs[i]
            }
            
            // We change the scope to the local scope, call the function body, then roll back to the global scope.
            let outerScope = this.scope
            this.scope = localScope
            let result = undefined
            for (let statement of bodyAsts) result = $(statement)
            this.scope = outerScope
            return result
        }
    }
}
```

`#name` will retrieve objects from the current scope, just like variables do :

```js
// Declaration
{ name: "#name", arity: 1 }

// Reducer
nameOp = ([name]) => this.scope[name]
```

Finally, using the `#call` operator, we can implement function calls :

```js
// Declaration
{ name: "#call", arity: [1, Infinity] }

// Reducer
let callReducer = ([obj, ...args]) => obj(...args)
```

And we're done ! Now, we can write (well, assuming arithmetic & `#print` are implemented) things like our previous add function, and it will work like a charm :

```
fun' add(x; y) x+y;

#print add(1; 9); // Prints 10 !
```
